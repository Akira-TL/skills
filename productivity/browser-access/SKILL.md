# Browser Access

## 一、目标

本 Skill 提供通用的浏览器访问层：先发现当前 Agent harness 已经提供的浏览器能力，再选择最小且足够的控制路径。它负责浏览器选择、可见交互、登录态复用、动态 DOM、网络请求解析和页面操作；上层 Skill 只描述“需要浏览器完成什么”，不应硬编码 Chrome、Playwright、CDP、Windows 或某个 Profile 路径。

浏览器不是默认工具。静态页面、公开资源或简单 HTTP 请求能直接完成时，优先使用 WebFetch / HTTP；只有遇到 JavaScript 动态页面、登录态、用户人工认证、浏览器安全上下文或真实交互需求时才进入本 Skill。

## 二、适用场景

优先在以下情况调用本 Skill：

1. WebFetch / HTTP 无法取得需要 JavaScript、登录态或浏览器安全上下文的页面内容。
2. 用户需要在可见浏览器中完成登录、验证码、二次认证或其他人工步骤，再由 Agent 继续。
3. 上层任务需要解析页面实际发出的资源请求，例如 PDF、数据文件或带会话信息的下载 URL。
4. 用户要求 Agent 检查、抓取或操作动态 DOM、虚拟列表、自定义控件或条件显示页面。
5. 用户要求自动填写问卷、报销表、申请表、报名表或其他网页表单，并保留最终提交的人工复核边界。
6. Agent 运行在 WSL、SSH、容器、远程开发环境或其他 harness 中，需要自行发现一个用户能看到并可持续复用登录态的浏览器。

如果任务只需要无状态静态抓取、普通 API 调用或批量 HTTP 下载，不要为了使用浏览器而使用浏览器。

## 三、浏览器能力发现与选择

每次需要浏览器时先做 **capability discovery**，不要先假定运行环境或浏览器实现。按以下顺序选择首个满足当前任务需求的能力。

### 3.1 首选：harness 原生或内联浏览器

先检查当前 Agent harness 是否已经提供浏览器、网页交互、页面控制或等价工具。只要它能满足当前任务需要的导航、页面读取、交互、登录延续或网络观察能力，就优先使用它，不再自行启动第二套浏览器。

如果 harness 浏览器缺少当前任务的关键能力，例如用户不可见、无法保留认证态、无法上传文件或无法观察真实网络请求，再升级到下一层；不要仅因熟悉 Chrome/CDP 就绕开更直接的原生能力。

### 3.2 次选：用户可见、可复用的浏览器

若 harness 内联浏览器不足，发现当前环境是否能够连接或启动用户可见的浏览器。优先复用已经存在、能够保持登录态的实例；没有合适实例时，再使用固定的持久 Profile 启动新的专用实例。

如果准备直接控制**用户自己的现有浏览器或 Profile**，且当前对话中尚未获得该浏览器/Profile 的明确授权，先向用户询问一次。用户同意后，在当前对话中把该浏览器 + Profile 视为已批准的 `Browser Grant`，后续任务直接复用，不重复询问。只有控制目标换成另一个浏览器、另一个 Profile 或权限范围明显扩大时才重新授权。

不要把“允许控制一个专用 Agent Profile”扩张成“允许控制用户日常所有浏览器 Profile”。

### 3.3 最后选择：自行建立 headed browser

当前环境既没有可用 harness 浏览器，也没有可复用的用户可见浏览器时，才自行建立 headed browser。必须使用稳定、可复用的 Profile，而不是每次创建临时 Profile。

在 WSL + Windows 场景中，优先复用固定 Windows Chrome CDP Profile；不可用时再考虑 WSLg Chromium。只有这些都不可行时才考虑 Xvfb/noVNC 等虚拟显示方案。具体 WSL → Windows Chrome、CDP 和命令模式按需读取 `REFERENCE.md`，不要把该环境特例当成通用浏览器默认。

一旦确定使用 WSL → Windows Chrome CDP adapter，先读取 `REFERENCE.md` 的确定性命令行界面（Command-Line Interface, CLI） 入口，并以 `scripts/browser_cdp.py` 作为默认控制面；浏览器生命周期、标签页发现、导航、页面勘察、点击、填写、等待、上传和网络观察优先通过该入口完成。

## 四、授权、Profile 与控制会话

### 4.1 Browser Grant

`Browser Grant` 至少绑定：浏览器/adapter、Profile identity 和当前允许的控制范围。它是对话级授权状态，不把浏览器密码、Cookie、token 或其他凭据写进项目文件。

- 已批准同一个浏览器 + Profile：直接复用。
- 未批准用户自有浏览器/Profile：先询问一次。
- 改用不同 Profile、不同浏览器或明显更高权限控制面：重新询问。
- harness 自身已经通过产品权限机制提供浏览器时，遵循 harness 的授权边界，不额外制造重复确认。

### 4.2 Persistent Profile

任何由本 Skill 自行创建的专用浏览器 Profile，统一使用固定 identity：`agent-browser`。浏览器关闭、崩溃或系统重启后，仍以这个 Profile 恢复；不能为了方便重新建立临时目录导致用户反复登录。

具体浏览器可以把 `agent-browser` 映射到自己的持久 data directory，但 identity 不变。用户日常 Profile 与该专用 Agent Profile 默认隔离。只有用户明确授权直接控制某个现有 Profile 时才连接它，而且后续始终绑定同一个既有 Profile identity，而不是把它重命名为 `agent-browser`。

### 4.3 登录与人工接管

Agent 可以导航到登录入口、选择机构入口、定位验证码区域并完成机械步骤。凡是已经识别为需要人工操作的步骤，按第十节进入强制人工接管：先把该步骤保留为待用户完成的明确边界，继续推进所有不依赖它的可自动化工作；在本轮任务推进结束时统一交给用户处理。用户完成后，Agent 应先验证页面已经进入预期状态，再继续原任务。

### 4.4 浏览器解析，Agent 传输

当上层任务需要 PDF、数据文件或其他 artifact 时，浏览器优先用于解析页面、继承授权并暴露真实资源请求。能从 DOM、页面状态或网络请求解析出最终 URL 时，返回 URL 及必要的临时请求上下文，让调用方直接传输；不要把“让浏览器下载到 Downloads 再找文件”作为默认流程。

需要建立 WSL → Windows Chrome CDP 通路、直接调用 CDP、处理跨系统文件路径或查看具体 DOM 表达式时，再读取 `REFERENCE.md`。

### 4.5 确定性执行层

选择 WSL → Windows Chrome CDP adapter 后，`scripts/browser_cdp.py` 是任务级默认执行层。命令与参数以脚本 `--help` 为准，不在任务中重新实现连接、target 发现、CDP 消息 ID、请求/响应或 WebSocket 生命周期。

- 常见页面动作直接调用脚本已有子命令；页面特定 DOM 逻辑通过它的 `eval` 执行。
- `click` 使用 CDP 指针事件完成真实点击；文本输入默认使用 `type`，由真实点击取得焦点后通过 CDP 键盘编辑命令与 `Input.insertText` 输入。
- `fill` 只作为原生 `input` / `textarea` / `select` 的 DOM 兼容兜底，不是普通表单的默认输入路径；`contenteditable` 不使用 `fill`。
- 脚本没有专用子命令的 CDP 方法通过 `call` 调用；需要捕获请求/响应时优先使用 `network`。
- `inspect` 默认只返回可见控件和文件控件，避免复杂网站的大量隐藏 DOM 占用上下文；确需检查隐藏控件时再请求完整列表。
- 已有脚本能力覆盖的操作不得另写 Python、JavaScript 或 WebSocket 包装脚本。只有 `eval`、`call`、`network` 等通用逃生口仍无法表达必须操作时，才把它视为执行层缺口；维护本 Skill 时优先扩展脚本和对应测试，而不是积累一次性实现。

## 五、先勘察，再填写

不要看到输入框就直接按 DOM 顺序批量赋值。先执行页面勘察：

1. 读取 `document.body.innerText`，确认页面标题、问题结构和当前可见内容。
2. 枚举 `input`、`textarea`、`select`、`button`、`[contenteditable=true]` 和 `input[type=file]`，记录 `id`、`name`、`type`、`value`、`placeholder`、`readonly`、`multiple`、`accept` 等属性；`contenteditable` 只表示 DOM 可编辑，不等于它是无内部状态的普通文本框。
3. 对问卷类页面，检查每道题所在容器的 `display` / `visibility`，识别条件题是否尚未展开。
4. 将字段与真实题目文本关联，不依赖“第 3 个 input 就是第 3 题”这样的脆弱假设。
5. 如果页面使用类似 `q1`、`q2_1`、`div3` 的编号，只把它们当作当前页面实现细节，不写成跨站点通用规则。

## 六、真实交互、条件题与动态字段

普通表单动作默认沿页面真实交互路径执行，而不是先修改 DOM 再人工派发事件：

- 文本 `input`、`textarea`、`contenteditable`：优先真实点击取得焦点后使用键盘输入；在 CDP adapter 中直接使用 CLI 的 `type`。
- 单选、多选、按钮和自定义选项：优先真实 pointer / mouse click；在 CDP adapter 中直接使用 CLI 的 `click`。
- 原生或自定义 `select`、日期选择器及其他组件：优先站点实际可见的原生交互；只有确认组件确实以普通 DOM 值为状态来源时，才使用 `fill` 或站点特定 `eval` 作为兼容兜底。

`contenteditable` 尤其不能仅凭 `textContent` 已改变就判断填写成功。富文本编辑器常有独立内部状态；如果真实输入后仍存在站点错误状态，应继续检查实际焦点、组件状态与监听目标，而不是改回 DOM 注入。

单选、多选或下拉选择可能触发后续题目显示。必须先完成上游真实交互，再重新读取可见字段。每次条件分支发生变化后，都要重新检查后续题目的显示状态，不能沿用填写前的 DOM 假设。

对于 `readonly` 日期框或复杂自定义组件，优先使用页面原生交互。如果确实只能使用兼容兜底，必须在操作后验证站点自身状态已经接受该值。

## 七、文件上传

上传前必须先确认：

1. 页面允许的文件数量；
2. 单文件或总大小限制；
3. `accept` 类型限制；
4. 是否要求把多张发票、截图和说明文件合并成一个压缩包或 PDF；
5. 浏览器进程实际运行在哪个操作系统。

如果浏览器运行在 Windows，而自动化脚本运行在 WSL，传给浏览器文件选择控件的路径必须是浏览器能访问的 Windows 路径。不要把仅 WSL 可见的 `/home/...` 路径直接交给 Windows Chrome。

当页面明确只允许上传一个文件，而用户还需要手动补截图、验证码或敏感材料时，应停止自动上传并把页面滚动到上传区域，让用户手动完成。不要为了“全自动”覆盖用户已有文件或反复触发上传错误。

## 八、提交安全边界

“提交”“发送”“确认付款”“发布”“删除”“授权”等不可逆或外部可见动作是硬边界。

在用户明确要求“先不要提交”“填好我确认后再提交”时：

1. 可以填写字段、展开条件题、滚动页面、上传用户明确授权的文件并做校验；
2. 不得点击提交按钮；
3. 不得调用 `form.submit()`、站点提交函数或等价 JavaScript；
4. 不得通过回车键、键盘快捷键或焦点切换意外触发提交；
5. 完成填写后，应把页面留在用户容易检查的位置；
6. 只有用户在后续消息中明确说“提交”“确认提交”或同等明确授权后，才执行最终动作。

不要把“用户之前同意开始自动化”解释为“用户已经同意最终提交”。

## 九、填写后的验收

在交还给用户检查前，至少验证：

1. 姓名、日期、金额、编号等关键字段的当前值或可见文本；
2. 单选/多选的组件状态确实改变，而不只是假定 DOM 属性已写入；
3. 对必填字段、自定义编辑器和受控组件，站点自己的 `required` / error / invalid 状态已经消失或转为预期状态；
4. 条件题是否按预期展开或隐藏；
5. 上传区域是否出现错误提示；
6. 当前页面仍停留在原问卷，而不是已提交的成功页；
7. 提交按钮尚未触发。

DOM 中“看得到值”只是一项证据，不足以证明受控组件已经接受输入。验收必须同时观察会受该交互影响的站点状态，例如错误提示、ARIA 状态、校验类名、条件题展开或其他组件反馈。

对于金额、发票号、订单号等容易出错的字段，应从用户提供的原始凭证或已核验文档中读取，不凭记忆猜测。

## 十、人机协作与强制人工接管

凡是已经识别为需要人工操作的步骤，该步骤立即退出自动化目标，进入强制人工接管。Agent 不因遇到人工步骤而提前放弃整轮任务，而是继续推进当前可完成的工作：

1. 标记该人工步骤及其依赖边界，保持当前页面、输入状态和登录上下文可供用户直接接手；
2. 继续完成所有不依赖该人工步骤、且仍可安全执行的机械化工作；依赖它的后续流程只能推进到该边界之前；
3. 若本轮出现多个人工步骤，在本轮任务推进结束时统一汇总，并把浏览器停在用户可以直接操作的位置；
4. 向用户明确说明已经完成的部分、需要人工完成的动作以及尚未触发的外部动作；
5. 用户完成后，下一轮先核验页面或认证状态，再从依赖边界继续执行。

典型人工步骤包括验证码、短信码、二次认证、机构登录、用户需要亲自选择或检查的附件、隐私/授权/支付/法律确认，以及任何用户明确要求自己处理的步骤。

**硬边界：不得为了继续自动化而尝试绕过、模拟、规避或替代已经识别出的人工步骤。** 自动化的目标是把其余工作推进到最接近该人工边界的位置，然后把真正需要人的动作交给用户完成。

## 十一、任务结束与浏览器生命周期

单次网页任务结束时默认只结束当前自动化动作，不破坏可复用的浏览器身份。

- harness 原生浏览器：遵循 harness 的生命周期，不主动清除其持久上下文。
- 用户已授权的现有浏览器/Profile：保留浏览器、Cookie 和登录态，不主动关闭、退出登录或清理 Profile。
- Agent 自行启动的专用浏览器：默认跨任务复用同一个持久 Profile；浏览器被关闭或系统重启后，仍以同一 Profile 恢复。
- 只有用户明确要求关闭或清理时才销毁专用实例/Profile；对用户自有 Profile 不执行清理。

使用 WSL → Windows Chrome CDP adapter 时，可通过 `localhost:9222` 重新发现现有实例和目标标签页；这是该 adapter 的恢复方式，不是其他浏览器实现必须遵循的协议。
